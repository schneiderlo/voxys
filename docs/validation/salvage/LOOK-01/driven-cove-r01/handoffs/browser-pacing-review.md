# Browser presentation pacing and F9 routing

The first browser journey was deliberately stopped after 237.308 seconds of its mechanism driver, after 14 partial stages and before the third boarding, following the disabled-propeller Launch. Initial forward/reverse/stopped checks, the reversed-setting check and both free refits completed; disabled-drive, cable, pause and save/reload completion did not. It is a failure, not a passed motion/save check. The original outer report, journey report and two read-only probes are retained. No image or game-state setter was used.

The single probe established a visible, focused AMD hardware page with approximately 1 FPS and 1,001 ms frame intervals at that observation, while CPU submission took 1.1 ms and GPU frame execution took 3.759 ms. There was no queue saturation or pacing skip. The old capped requestAnimationFrame schedule was therefore held by browser/window scheduling; this was not a demonstrated GPU throughput limitation or failed navigation permission. The probe does not establish the operating-system cause of the scheduling restriction or a constant frame rate throughout the run.

The revised journey sends the documented real F9 key to select the existing uncapped scheduler, checks its read-only status, and repeats the same input after page reload. Native journeys already use the existing --uncapped option. At that first revision only the driver changed; its numerical acceptance limits were unchanged.

The second journey failed after 10.032 seconds with zero recorded stages: `F9 uncapped input was not accepted`. Its real key edge reached the ordinary input queue, but existing `Application::handleKeyboardShortcuts` returned for the Cove before reaching F9; the workshop guard also preceded that handler. Root moved the existing F9 toggle immediately after the null-input guard, before both experience/workshop returns, and removed its former location. This is a required Application shortcut-routing fix; no other bindings, renderer, simulation or save behavior changed. Both r06 Application builds are running.

The passing native r06 motion journey used native-r04 before this F9-only fix and its existing command-line uncapped option. That result remains valid for its exact package; no full native motion replay is claimed for the later package. Browser F9 and full journey acceptance require the rebuilt package. No numerical acceptance limits are relaxed. This is behavior verification, not a frame-time certification.

## The documented F9 shortcut was unreachable in Cove

Browser r02 failed after 10.032 seconds with zero recorded stages because physical F9 did not change the read-only uncapped status. Source investigation found that handleKeyboardShortcuts returned for salvage preview before its F9 binding, and returned even earlier for an open workshop. The real input queue preserves press edges; sending the key was not sufficient to reach the binding.

The existing F9 toggle is now handled immediately after the nonnull input guard, before experience/workshop gameplay guards; its old later binding is removed. Other shortcuts and simulation/save code are unchanged. This is an application correction following the first pacing diagnosis, so the earlier proposed input-only correction was insufficient. Both application packages must be rebuilt. The next browser journey requires the real key to work initially and after restore. The already passed native full motion journey remains evidence for unchanged motion behavior; its binary precedes this isolated shortcut relocation, which is explicitly recorded.
